# TISSCA Cross-Platform Identity Contract Audit

**Status**: READ-ONLY AUDIT. No schema changes. No migrations. No implementation.  
**Date**: 2025-07  
**Scope**: All ID fields across Android, iOS, Website, and Supabase schema  
**Purpose**: Establish the real canonical identity architecture before any
cross-platform linkage work is designed.

---

## 1. Executive Summary

TISSCA has **two diverged identity systems** that share the same Supabase tables:

| Origin | Identity used in `tool_attachments.parent_id` | Identity used in `crm_history` |
|--------|----------------------------------------------|-------------------------------|
| Android | `leads.client_record_id` / `jobs.client_record_id` | `workspace_id` |
| Website | `leads.id` (Postgres UUID PK) / `jobs.id` (Postgres UUID PK) | `business_id` or `workspace_id` |

These two values **never collide and cannot be joined** without a resolver step.
No single column exists today that safely bridges across both identity systems
for all data flows.

**iOS**: Based on all available evidence, iOS is absent from this codebase. No Swift,
no iOS-specific DTOs, no iOS-scoped API routes, no iOS platform markers in `documents`.
iOS alignment state is **UNKNOWN / NOT IMPLEMENTED**.

### 2.2 `client_record_id` — Mobile-Generated UUID

| Attribute | Value |
|-----------|-------|
| Type | `text` (stored as text, semantically a UUID string) |
| Tables with this column | `leads`, `jobs`, `tasks`, `tool_attachments` |
| Tables WITHOUT this column | `clients`, `quotes`, `invoices`, `documents`, `quote_items`, `invoice_items`, `quote_acceptance_snapshot` |
| Origin | Generated by Android app (Kotlin `UUID.randomUUID().toString()`) before any Supabase write; assigned at object creation time on device |
| iOS origin | UNKNOWN — not observable from this codebase |
| Website origin | Website creates `tasks` with `crypto.randomUUID()` (a web Crypto API call) — same entropy, different generator |
| Website usage on leads/jobs | Website sets `client_record_id: input.client_record_id ?? null` on leads/jobs — it accepts but does not generate one for new website-created leads/jobs |
| Local-only? | ❌ No — synced to Supabase, but NOT the primary Supabase PK |
| Cross-platform? | ✅ This is the Android cross-platform identity for a CRM entity |
| Survives sync? | ✅ Yes — set by the origin device, never changed after creation |
| Canonical? | ✅ **Android-canonical identity for leads, jobs, tasks, and tool_attachments** |
| Legacy? | ❌ Not legacy — it is the authoritative mobile identity |
| Safe for SQL joins? | ⚠️ Yes for Android↔Android; **UNSAFE for website↔Android** because website does not consistently generate one |
| Safe for cross-platform architecture? | ⚠️ Only if BOTH platforms populate it. Website currently leaves it NULL for new leads/jobs created via the website CRM |

**Critical observation**: `tool_attachments.client_record_id` is stored as `text`,
not `uuid`. This means Android passes its own UUID-format string; the website receives
it as-is. The column on `tool_attachments` was added in `security_p0_data_isolation.sql`
specifically to accept Android-originating values.

## 4. Unsafe Joins

The following joins are **architecturally unsafe** — they will silently return
incorrect or incomplete results depending on the data origin platform.

### 4.1 `tool_attachments.parent_id → leads.id` (partial match only)

```sql
-- UNSAFE: Only finds website-created tool attachments
SELECT ta.*
FROM tool_attachments ta
JOIN leads l ON ta.parent_id = l.id
WHERE ta.parent_type = 'LEAD'
```

**Why unsafe**: Android rows have `ta.parent_id = l.client_record_id`, which is a
different UUID from `l.id`. This join silently drops all Android-created attachments.

### 4.2 `tool_attachments.parent_id → jobs.id` (partial match only)

Same problem as above for jobs. Website-created jobs expose `jobs.id` as the join
key; Android-created jobs expose `jobs.client_record_id`.

### 4.3 `quotes.client_id → clients.id → leads.client_record_id` (broken path)

```
quotes.client_id → clients.id
                              ↓
                  clients has NO client_record_id column
                              ↓
                  DEAD END
```

There is no path from `public.quotes` to `leads.client_record_id` through any
current column.

### 4.4 `documents.linked_entity_id → quotes.id` (works only for website docs)

Android-created documents have `platform = 'android'` and may not set
`linked_entity_type` / `linked_entity_id`. A join on these fields will silently
exclude Android documents.

### 4.5 `reassignToolAttachmentsToJob(leadId, jobId)` (partial reassignment)

```typescript
// In workspace-data.ts
.update({ parent_id: jobId, parent_type: 'JOB' })
.eq('parent_id', leadId)   // ← leadId = leads.id (website PK)
.eq('parent_type', 'LEAD')
```

This only reassigns tool_attachments where `parent_id = leads.id`. Android-created
attachments where `parent_id = leads.client_record_id` are **not touched** by this
operation and remain orphaned to the lead after job conversion.

## 5. Current Parity Gaps

### Gap 1 — `tool_attachments.parent_id` identity split

**Status**: Active divergence  
**Symptom**: Website lead detail page shows tool cards filtered by `parent_id = leads.id`.
Android app sees tool cards filtered by `parent_id = leads.client_record_id`.
A workspace with both website-created and Android-created tools will show **different
subsets** on each platform.

### Gap 2 — Lead→Job conversion does not propagate `client_record_id`

**Status**: Active bug  
**Evidence**: In `leads/[id]/convert/route.ts`, `createJob(...)` is called WITHOUT
passing `client_record_id: lead.client_record_id`. Therefore:

```
lead.client_record_id = "android-uuid-abc"
    ↓ convert
job.client_record_id = NULL  (not propagated)
```

After conversion, the job has no mobile identity. Android cannot find the job by
`client_record_id`.

### Gap 3 — `tool_attachments` reassignment skips Android rows

**Status**: Active data loss on conversion  
**See**: Unsafe Join 4.5 above. Android tool attachments are not reassigned to the
new job.

### Gap 4 — `public.clients` has no `client_record_id`

**Status**: Missing column  
**Impact**: There is no path from `quotes.client_id` or `invoices.client_id` to any
mobile identity. The entire quote/invoice system is disconnected from mobile.

### Gap 5 — Website leads/jobs may not have `client_record_id` set

**Status**: Active gap for website-created entities  
**Evidence**: `createLead(...)` passes `client_record_id: input.client_record_id ?? null`.
When a lead is created from the website CRM (not a tool handoff from Android),
`client_record_id` is `NULL`. Android cannot identify this lead by mobile UUID.

### Gap 6 — `crm_history` dual scoping creates ambiguous queries

**Status**: Architectural debt  
**Evidence**: `crm_history` has both `business_id` and `workspace_id` columns.
CRM events (leads, jobs) use `business_id`; task events use `workspace_id`.
`getHistory()` merges both scopes and deduplicates. In post-P0 schema these are
the same UUID, so this is harmless but confusing.

### Gap 7 — System B documents only appear in member app after PDF generation

**Status**: Known by design but undocumented risk  
**Evidence**: `persistDocumentAndLog()` is called fire-and-forget from within PDF
routes. If a staff member creates a quote in the web portal but never generates
a PDF, the quote is invisible in `/app/quotes`.

### Gap 8 — iOS platform state unknown

**Status**: Unknown / Not implemented  
**Evidence**: No iOS-specific code, DTOs, or platform markers found anywhere in
the website codebase. `platform` column on `documents` accepts `'web'` or `'android'`;
no `'ios'` value is used.

## 6. Android vs Website Divergences

### Identity model

| Dimension | Android | Website |
|-----------|---------|---------|
| Lead identity for attachments | `leads.client_record_id` | `leads.id` (Postgres PK) |
| Job identity for attachments | `jobs.client_record_id` | `jobs.id` (Postgres PK) |
| Task identity | `tasks.client_record_id` (always set) | `tasks.client_record_id` (generated via `crypto.randomUUID()`) |
| Quote identity | In `public.documents` (type='quote') | In `public.quotes` + mirrored to `public.documents` after PDF |
| Invoice identity | In `public.documents` (type='invoice') | In `public.invoices` + mirrored to `public.documents` after PDF |
| Contact/client identity | Inline on lead/job (client_name, phone, email) | In `public.clients` (separate table, FK'd) |
| `clients` table | Not used (no `client_record_id` column) | Used for structured contacts |
| Timestamp format | Epoch millis (`created_at_millis`) | Both epoch millis AND ISO timestamptz |

### Data flow

| Flow | Android | Website |
|------|---------|---------|
| Create lead | Writes to `public.leads` with `client_record_id`, full contact inline | Writes to `public.leads` with optional `client_id` FK, `client_record_id = null` |
| Create tool attachment | `parent_id = lead.client_record_id` | `parent_id = lead.id` (Postgres PK) |
| Convert lead→job | Moves attachments by `client_record_id` | Moves attachments by `leads.id` PK |
| Create quote/invoice | Writes to `public.documents` (type='quote'/'invoice') | Writes to `public.quotes`/`public.invoices`; mirror to `public.documents` only on PDF generation |
| View quotes in app | `/app/quotes` reads `public.documents` | Staff views from `public.quotes`; client views from `public.quotes` |
| PDF generation | Via `/api/workspace/documents/:id/pdf` (tool-payload.ts) | Via `/api/quotes/:id/pdf` or `/api/invoices/:id/pdf` |

## 8. IDs That Should NEVER Be Used for Cross-Platform Linkage

### ❌ `tool_attachments.parent_id` as a direct join key

**Reason**: Contains two incompatible namespaces. Android rows use
`client_record_id`-space; website rows use Postgres PK-space. No query can
distinguish them without additional context.

### ❌ `business_id` in new code

**Reason**: Legacy alias for `workspace_id`. The `public.businesses` table is
effectively replaced by `public.workspaces`. New code must use `workspace_id`.

### ❌ `job_id` / `lead_id` on `tool_attachments` (original bootstrap columns)

**Reason**: Superseded by `parent_id + parent_type`. Legacy rows only.

### ❌ `quotes.id` or `invoices.id` as a universal document reference

**Reason**: Android does not write to `public.quotes` or `public.invoices`. Using
these IDs as the document reference excludes all Android-origin quotes/invoices.
`documents.id` is the cross-platform document reference; `documents.linked_entity_id`
is the provenance back-link.

### ❌ `clients.id` as a cross-platform entity identity

**Reason**: `public.clients` is a website-only contact table. Android does NOT write
to it, and the table has no `client_record_id` column to bridge back to mobile.
Android carries contact data inline on leads/jobs.

### ❌ `leads.id` or `jobs.id` as `parent_id` for cross-platform tool attachment creation

**Reason**: If an Android device creates a tool attachment in the same workspace,
it uses `parent_id = leads.client_record_id`. The website uses `parent_id = leads.id`.
Using either as the canonical join key will exclude the other platform's attachments.

## 9. Future-Safe Architecture Recommendation

### Principle 1 — Adopt `client_record_id` as the canonical mobile-side identity

`client_record_id` is the Android contract for cross-platform identification. It is:
- Generated before sync (works offline)
- Immutable after creation
- Present on `leads`, `jobs`, `tasks`, `tool_attachments`
- Already stored in Supabase

**Action required**: The website must generate and store `client_record_id` on ALL
new leads and jobs it creates, not just when passed from Android. This closes Gap 5.

```typescript
// In createLead / createJob on website:
client_record_id: input.client_record_id ?? crypto.randomUUID(),
//                                          ^^^^^^^^^^^^^^^^^^^
//                                          generate if not provided
```

### Principle 2 — Propagate `client_record_id` through lead→job conversion

In `leads/[id]/convert/route.ts`, the `createJob` call must pass:
```typescript
client_record_id: lead.client_record_id,  // propagate mobile identity
```
This closes Gap 2 and ensures jobs created from leads are findable by mobile.

### Principle 3 — Normalise `tool_attachments.parent_id` namespace

**The safest long-term solution**: Store `parent_id = entity.client_record_id` for
ALL tool attachment writes, both website and Android. This makes the namespace
consistent.

**Migration path**:
1. Backfill `tool_attachments.parent_id` for website-created rows where
   `parent_type = 'LEAD'`: set `parent_id = leads.client_record_id WHERE
   tool_attachments.parent_id = leads.id`
2. Backfill similarly for jobs
3. Update website tool attachment creation to use `client_record_id` as parent_id
4. Update `reassignToolAttachmentsToJob` to use `client_record_id` as the join key

**Risk**: Requires data migration (leads that have no `client_record_id` must get one
first). Website-created leads with NULL `client_record_id` cannot be migrated until
Principle 1 is applied and backfilled.

### Principle 4 — Add `client_record_id` to `public.clients`

If `clients` gain a `client_record_id` column, the path:
```
quotes.client_id → clients.id → clients.client_record_id → leads.client_record_id
```
becomes possible. This is the **most conservative bridge** for quote/invoice → CRM
linkage without altering `public.quotes` or `public.invoices`.

**Prerequisite**: Verify whether the live Android schema populates `clients.client_record_id`
before designing around it.

### Principle 5 — `workspace_id` is the universal tenant scope key

All new tables and columns must use `workspace_id` as the tenant scope key. No new
`business_id` references should be introduced. Existing `business_id` columns on
`quotes` and `invoices` are grandfathered; they equal `workspace_id` in live schema.

### Principle 6 — `documents` is the cross-platform display layer for quotes/invoices

Do not attempt to merge `public.quotes` and `public.documents`. Instead, ensure that:
- System B (web portal) quotes always write to `public.documents` at first PDF
- `documents.linked_entity_type + linked_entity_id` is populated for all web-native docs
- Android documents are accepted as-is (they are already correctly writing to `public.documents`)
- The member app (`/app/quotes`, `/app/invoices`) continues to read from `public.documents`

### Principle 7 — `crm_history.client_event_id` for cross-platform dedup

The website should set `client_event_id` on all history events using the same
`"${entityId}:${action}:${timestamp}"` format to prevent duplication when Android
or iOS also logs the same event.

## 10. Schema Evolution Summary (Chronological)

Understanding how the identity model evolved helps explain the current gaps.

| Phase | Change | Identity impact |
|-------|--------|----------------|
| Prisma (legacy) | `quote`, `invoice`, `lead`, `job` tables with CUID PKs, `userId`-scoped | Completely separate from mobile; dead for member app |
| `phase_c1_quotes.sql` | Created `public.clients`, `public.quotes`, `public.materials` with `business_id` | Introduced `client_id` FK; no mobile identity |
| `phase_d1_invoices.sql` | Created `public.invoices` with `client_id`, `quote_id` | Extended System B; still no mobile identity |
| `bootstrap_tool_attachments.sql` | Created `tool_attachments` with `lead_id` + `job_id` columns (separate FKs) | Original website-only model using Postgres PKs |
| `phase_tools_parity_columns.sql` | Added `tool_key`, `tool_title`, `values_text`, `total`, `raw_payload` | Parity columns for Android compatibility |
| `phase_f2_crm_client_links.sql` | Added `leads.client_id` + `jobs.client_id` FKs to `clients` | Connected CRM to website contacts (not mobile) |
| `bootstrap_documents.sql` | Created `documents` table with `linked_entity_type + linked_entity_id` | Introduced cross-platform document layer |
| `security_p0_data_isolation.sql` | Added `workspace_id`, `parent_id`, `parent_type`, `client_record_id` to `tool_attachments` | **Critical**: introduced Android parity columns; now two parent_id namespaces exist in same table |

| DEFERRED W5 | Would have added `lead_id`/`job_id` to `quotes`/`invoices` using Postgres PKs | **Rejected**: used wrong identity (PKs instead of `client_record_id`) |
